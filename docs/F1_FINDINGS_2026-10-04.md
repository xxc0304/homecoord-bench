# F1：已审结果中的冲突、服务与时延发现

2026-10-04。本轮仅解读已验收的F1统计：2个基础模板、8配置、3策略×3固定返回顺序，共72条确定性回放、168对比较和18组四单元。没有新增实验；以下是作者基于受审数据的描述性分析，不是对论文主张的独立审查或真实模型性能验证。

验收依据：外部 `F1_AGGREGATION_V1_REVIEW_20261004.md`。追加限定验收记录为 `F1_AGGREGATION_V1_ACCEPTANCE_2026-10-04.json`；原结果中的历史pending字段不改写。数值、源运行指针和事件下标见 `f1_findings_20261004/evidence.json`，提取脚本为 `../homecoord_bench/task_revision/f1_findings_20261004.py`。

## 1. 最明确的发现：安全、完成和按时不能互相替代

72条运行全部完成预定服务，实际执行容量违规持续时间均为0，开始前置条件诊断也均有效。但有4条任务迟到：均为五负载模板D-F1-02、容量紧、基准期限中的water，出现在GateRetryRule与ConstraintCoordinator的order1/2。

共同安全门下，“最终完成且没有超容量”仍可能漏掉紧期限服务。这里的冲突表现不是设备真的超载，而是竞争导致的门拒绝、排队、重排及个体等待。不能用一个总成功率或冲突次数覆盖这些维度。

五负载、容量紧、基准期限的逐顺序结果如下。每个运行必需且完成的任务数均为5；order0/1/2分别是原序、逆序、左旋。

| 策略 | 按时任务数（order0/1/2） | water完成时间ms（order0/1/2） | 全户完工ms（order0/1/2） |
| --- | --- | --- | --- |
| GateRetryRule | 5 / 4 / 4 | 240900 / 661300 / 661100 | 901000 / 1200900 / 1141100 |
| ConstraintCoordinator | 5 / 4 / 4 | 240900 / 720900 / 901300 | 900900 / 901100 / 901300 |
| DeadlineAwareCoordinator | 5 / 5 / 5 | 241700 / 241700 / 241700 | 1141700 / 1141700 / 1141700 |

water截止为360000ms。这张表不是全项目排名，只描述一个资源/期限配置的三个固定返回情境。

## 2. 主动排队减少门拒绝，不等于各项时延都更好

上表中GateRetryRule的容量门拒绝次数为3/2/2，ConstraintCoordinator为0/0/0，但后者的容量defer次数为3/2/2。前者是先尝试再被门拦截、随后重试；后者提前安排容量等待。门拒绝减少与真实执行违规减少是两件事；此处两者真实违规本来就都是0。

三负载、容量紧、基准期限、order0的简单例子：dishes在GateRetryRule中181200ms启动、481200ms完成；ConstraintCoordinator中181100ms启动、481100ms完成。两个都按时，主动排程仅早100ms。这个差值来自此合成实现的调度/命令时序，不能解释为实测网络或协调计算开销。

另一方面，五负载同配置的order2中，ConstraintCoordinator比GateRetryRule全户早239800ms完工（901300对1141100），却使water晚240200ms完成（901300对661100），water迟到量从301100增至541300ms。**整体完工更快可以掩盖紧期限任务等待更久。**

这支持报告逐任务等待与迟到，而不是预设某种协调机制全指标占优。

## 3. 期限感知在这组紧期限任务上有效，但不保证更早全户完工

DeadlineAwareCoordinator在上表三个顺序中均让water按时，完成时间均为241700ms；三种策略仍完成同样5项服务。其全户完工却为1141700ms：比ConstraintCoordinator三个顺序都晚，在order0还比GateRetryRule晚240700ms。因此这里体现的是紧期限服务与完工时间之间的取舍，而非所有时间指标共同变好。

反例也来自三负载模板：容量紧、基准期限、order0时三种策略全服务按时，DeadlineAwareCoordinator完工661300ms，GateRetryRule为481200ms、ConstraintCoordinator为481100ms。期限感知并不是无条件更快；仅看五负载紧期限配置会漏掉这个负对照。

当前DeadlineAwareCoordinator实现等待已发布任务的提议返回后再按期限排程（`../homecoord_bench/runtime/event_simulator.py`中的`try_dispatch_deadline_batch`）。这不是纯粹改变排序的单因素方法消融；不能把结果全部归因于期限优先规则本身，或声称所有EDF算法有同样返回顺序敏感性。源实现与实际时间表共同限定解释。

## 4. 容量与期限改变结论；期限放宽不等于执行加速

容量足的36条运行全部按时，没有容量门拒绝或容量defer。其中GateRetryRule与ConstraintCoordinator的12对比较，各任务启动/完成等时间完全相同。这是“额外协调在该条件下没有可见时间增益”的有效负对照，不是应删掉的无冲突场景。

36对基准/宽松期限比较中，实际返回、启动、完成和执行时间均不变。宽松期限只是各截止增加1200000ms；原来的4项迟到因此变成按时。不能将按时率提高写成调度更快。也不能外推“期限不会改变调度”：这里只是两套期限参数没有改变当前实现的实际排程。

三负载模板在全部配置/顺序中已经全服务按时；五负载模板的迟到仅出现在容量紧+基准期限+特定顺序的组合。容量足或期限放宽时，本文这项按时差异消失。这是条件依赖的描述，不是资源不足或损失不可避免的证明。

18组四单元在当前数据中四臂都完成全部E，因此K=E、覆盖率100%。没有完成集合选择导致的时间比较覆盖差异；共同K只是本批条件比较的合法对象，仍不支持普遍因果效应。

## 5. 对主研究问题的收获

主问题仍是多Agent调度过程中的冲突—服务—时延权衡，不改成LLM调用时机。

- **P1：竞争的影响有条件。** 容量压力、期限和返回顺序共同决定这里是否出现迟到；没有竞争的对照同样有研究价值。
- **P2：无违规、服务完成、按时与全户完工不可替代。** 本批全部安全完成仍出现迟到；更早全户完工也能让紧任务更晚。
- **P3：协调机制没有单一、无条件的收益。** 主动排队可以减少被门拒绝的尝试；期限感知可以保护这组紧任务；简单规则在容量足/期限足够时也能完成服务。这些收益须连同个体等待和负对照报告。

这是对已审F1合成材料的证据解释，不是上述主张在任意家庭、多模型或未知任务中已获验证。当前没有实测协调计算时钟、真实API时间或实机响应，不能给出完整通信/计算成本曲线、P99或显著性结论，也不说明LLM相对规则的优势。
