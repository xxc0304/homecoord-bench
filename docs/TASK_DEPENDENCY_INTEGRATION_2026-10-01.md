# 洗→烘任务依赖：统一事件执行器 v3

状态：作者定义的抽象开发任务；离线集成验证，未独立人类双审、非物理设备或模型性能证据。无 API 调用、未读取保留测试、未上传 GitHub。

## 本轮完成什么

把 HC-M12 原来只有文字的“洗完触发烘干”修订为显式 `depends_on: [wash]`。烘干可以提前提出请求，也可以提前返回有条件的提案；执行器将合法提案保存在依赖等待队列，直到获得**实际完成、动作匹配、未撤回的前驱回执**才送入普通调度。启动时仍复核依赖和工具的 `laundry.washed=true` 前提。

新入口为 `homecoord_bench.task_revision.event_simulator_v3.run_event_simulation`：从 v2 派生，依赖与停止、恢复、权限、状态事件、容量门控共享同一队列。v1/v2 源码、旧入口和旧结果均保持不变；v3尚未替换默认 CLI。无依赖时，14个原语义情境及10个生命周期情境×4策略，共96组 v2/v3 完整轨迹和评分一致性检查通过。

依赖图检查未知前驱、重复边、自依赖、非法字段及环路。支持多前驱全部完成、三任务串联和取消沿依赖链传播；这些额外图形目前是单元测试，不擅自计入已审核 benchmark 结构。

## 请求发布不等于可执行

正常的提前请求轨迹如下：

| 事件 | 仿真时刻 |
|---|---:|
| 烘干请求发布 | 100ms |
| 烘干条件提案返回，进入等待 | 400ms |
| 洗涤实际完成，依赖释放 | 4400ms |
| 烘干开始，支付100ms命令延迟 | 4500ms |
| 烘干实际完成 | 8500ms |

烘干响应时延按它自己的发布时刻计算，为8400ms，不是8500ms。晚发布匹配对只将烘干发布改为5000ms；启动5400ms、完成9400ms，自身完成时延4400ms。新字段 `dependency_dispatch_ready_at_ms` 表示合法提案进入调度的时刻，不冒充所有条件最早满足时刻或实际启动时刻。

这里的4000ms洗/烘周期、功率和提案延迟均为作者抽象合同，**不代表真实洗衣机四秒洗完**。场景目标使用实际动作完成回执，不靠外部事件满足。

## 九个情境的处置

| 情境 | 检验的问题 | 开启依赖的实际结果 |
|---|---|---|
| 提前请求 | 请求与前提时间分离 | 提案等待，洗完后烘 |
| 晚发布 | 只有发布时间改变 | 不在发布前调用/执行；已满足前提时正常服务 |
| 紧截止 | 期限是否真的计分 | 8500ms完成、截止8000ms，超期500ms，不填成功 |
| 洗涤取消 | 停止/作废旧完成是否释放依赖 | 洗/烘无完成回执；烘干明确 blocked，时延 null |
| 洗涤恢复 | 首次被取消的尝试不能算前驱完成 | 5100ms从零重洗，9100ms完成，烘干9200→13200ms |
| 伪造状态 | `washed=true`能否替代真实服务 | 450ms外部状态改真仍须等待4400ms真实回执 |
| 洗涤提案失败 | 非法操作是否被算完成 | 严格工具校验拒绝，烘干 unresolved/waiting，不执行 |
| 容量紧 | 独立第三负载与后继任务竞争 | 容量调度/重试策略完成；无重试 Independent 可丢失烘干服务 |
| 容量足 | 只改容量的匹配对照 | 第三负载与洗→烘链合法并行 |

洗涤已撤回但停止确认过迟、自然完成的负测试也通过：它可以有物理完成事件，但不是未撤回的有效前驱回执，因此不会继续自动烘干。失败提案目前没有自动修复或终止后继的完整失败协议；保留 unresolved，而不是虚构恢复。

## 必要依赖与容量竞争分开

主洗→烘两任务必须串行，所以不能因为1.5+2.0kW超过限额就声称它们存在可并发的 C3 冲突。基础情境移除了原无意义的容量冲突标签。

容量对照另加入独立洗碗服务：洗涤1.5kW、洗碗1.5kW，可以在3kW下并行；后续烘干2kW与仍运行的洗碗服务会超过3kW。容量足对照只把阈值改为6kW。

Constraint 策略下，容量足时烘干4500ms开始；容量紧时等待洗碗8400ms结束再开始。GateRetry 在释放后另支付命令延迟，8500ms开始。Independent 无容量重试的情况合法拒绝但未完成烘干，保留负结果；不把依赖等待器包装为自动解决全部容量调度。

## 离线结果与证据边界

9情境×4策略×依赖等待开关，72次脚本执行、36个匹配对。使用同一答案模板、300ms提案延迟和共享安全门；开关控制是执行机制诊断，**不是模型架构实验**。所有保存轨迹均经过独立物理状态/取消/预约重放，以及按事件顺序重计的完成 DAG 审计。

| 计数 | 不启用依赖等待 | 启用依赖等待 |
|---|---:|---:|
| 取得所有动作完成回执的执行单位 | 10/36 | 27/36 |
| 完成动作数 | 46/80 | 63/80 |
| 没有洗涤完成回执就启动烘干 | 4 | 0 |

关闭组4条错误启动来自伪造状态情境：最终洗/烘目标可以都满足，但执行顺序不合法，因此不能把“取得完成回执”称为正确流程成功。开启组未全服务包括明确取消、非法前驱提案和一个无重试容量策略；这些并非都应通过更多模型调用修补。合理取消另计处置，不能算动作完成。

目前只有**两个抽象图拓扑**：洗→烘链，以及同一链加独立第三分支；9是配置数，不是9个独立任务结构。结论是依赖与计分基础设施得到验证，不证明 LLM 必需、多 Agent 优越或真实家庭可部署。
