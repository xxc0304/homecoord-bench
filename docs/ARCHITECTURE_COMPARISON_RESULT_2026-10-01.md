# 同模型集中／功能 Agent 开发比较：真实试点结果

完成预登记的 224 次 DeepSeek 请求、72 个策略执行单位，以及独立发布状态/完整轨迹回放审计。224 个预算预约、调用开始和终止事件一一对应，均为一次尝试，没有重试或补采。206 次通过协议校验，18 次收到模型输出但未通过校验；没有观察到 HTTP、SSL、网络或超时失败。API 预算已用满。保留测试未打开，本轮仅本地保存。

## 运行范围与结果

按事前固定的六个开发结构、竞争/无竞争条件、两次重复，比较集中批次、功能局部和功能同批汇集三组。三组同用模型标识 deepseek-flash、非思考模式、DeadlineAwareCoordinator 与安全门。每个条件重新采样，晚到请求按各分支 release 现场构造；不能把不同模型选择/返回时延的差异称作固定提案的纯调度因果效应。

| 组 | API 请求 | 校验失败请求 | 最终全部服务 | 全部按时 | 合规且服务选择正确的任务 |
|---|---:|---:|---:|---:|---:|
| 集中批次 | 32 | 7 | 18/24 | 16/24 | 85/96 |
| 功能局部 | 96 | 7 | 17/24 | 15/24 | 89/96 |
| 功能汇集 | 96 | 4 | 20/24 | 17/24 | 92/96 |

所有 72 单位均计入分母，包括失败。集中批次原子校验导致一次失败可影响多项任务：7 次请求校验失败对应 11 项无效提案；局部 7 项、汇集 4 项。缺失正确启动/完成为 null，未用零掩盖。72 个执行的状态约束违规时间均为 0；安全门拒绝或无动作不等于完成服务。

266 项通过协议/授权检查的任务提案全部选中了合法服务；其余 22 项是协议失败影响的任务，而非已证明的需求理解错误。总体服务与按时差异受接口可靠性影响，当前表不支持全局架构优越性或稳定统计结论。

| 组 | 输入 Token（含失败） | 输出 Token（含失败） | 整个发布组采集墙钟中位数 | 单请求完整返回中位数 |
|---|---:|---:|---:|---:|
| 集中批次 | 97,140 | 12,754 | 1,850.5 ms | 1,849 ms |
| 功能局部 | 135,988 | 11,993 | 1,172.5 ms | 1,002.5 ms |
| 功能汇集 | 389,568 | 12,440 | 1,191 ms | 1,076 ms |

各组均有 32 个发布组观测；功能组内请求真实并发，因此整组完成耗时不是各调用时间求和。集中输出包含多个任务，功能每请求只输出一个任务，单请求中位数仅为描述性统计。整组采集墙钟包括本地构造/校验/日志和线程管理，不是设备端到端响应时间；模拟器按实际返回偏移安排虚拟提案事件。

本轮集中请求数为功能组的三分之一，集中输入 Token 也更少，但发布组采集中位数更长。汇集功能输入 Token 约为局部功能的 2.865 倍、集中的 4.010 倍，来源包括重复发送汇集视图。这里已经有真实请求与 Token 用量证据，尚未核实缓存计价、账单或美元费用，不能将请求缩减比例等同于货币成本缩减比例。

总输入 622,696、输出 37,187 Token，224 次请求全部有 usage 记录，包含校验失败。日志 model 字段为 deepseek-flash；适配器在响应不含 model 时会回退请求标识，不凭这一字段确认底层权重版本。

| 家族/资源 | 集中 全服务/全按时 | 局部 全服务/全按时 | 汇集 全服务/全按时 |

| F1 固定/无竞争 | 4/4，4/4 | 4/4，4/4 | 2/4，2/4 |
| F2 晚到/竞争 | 2/4，0/4 | 2/4，0/4 | 3/4，0/4 |
| F2 晚到/无竞争 | 1/4，1/4 | 0/4，0/4 | 4/4，4/4 |
| F3 多模式/竞争 | 4/4，4/4 | 3/4，3/4 | 4/4，4/4 |
| F3 多模式/无竞争 | 3/4，3/4 | 4/4，4/4 | 3/4，3/4 |

各格仅两个结构×两重复。F1/F3 中协议合规单位均按时；部分无竞争条件仍丢服务，是接口失败，不能归因于资源冲突或强规则不足。

F2 竞争中有 7 个协议合规且最终全部服务单位，它们仍全部超期。D-F2-01 的热水从自身发布算起等待约 721–722 秒，超期约 601–602 秒；D-F2-02 等待约 421 秒，超期约 361 秒。它们对应早期不可中断承诺与晚到需求的资源排队机制，不是这几秒 API 时延足以解释的现象，也不证明所有在线强方法无解。其余 F2 单位还需分开看协议失败，不能把缺失提案都叫调度失败。

F3 同一需求的合法模式仍有个体等待和全计划完成取舍。例如 D-F3-01 竞争第一次采样：汇集功能选 eco，洗衣约 1.142 秒启动、全计划 601.142 秒完成；集中选 fast，洗衣约 242.030 秒启动、全计划 482.030 秒完成；局部也选 fast，洗衣约 241.226 秒启动、全计划 481.226 秒完成。快速模式下全计划早约两分钟，洗衣启动却晚约四分钟。它展示指标含义，并非同提案对照或集中结构胜利：局部也做出相同模式选择，第二次汇集采样同样选 fast。

## 18 次校验失败的检查

| 本地错误 | 次数 | 当前解释 |
|---|---:|---|
| 批次 task_id 未匹配当次任务 | 7 | 集中输出采用 release_batch 或带该前缀的 ID，未忠实关联 task_requests 的任务 ID |
| 用 type 替代 response_type | 6 | 功能输出字段不符合公共单任务协议 |
| requires 缺 range_min/range_max | 5 | 功能输出省略严格协议要求的空值字段 |

18 次均保存原始输出，原始文本长度未达到适配器 4000 字符截断上限。集中批次请求的顶层 task.task_id=release_batch 是记录用占位标签；模型将它用作任务 ID 是输出可见现象。该占位标签可能造成接口歧义，是当前基于轨迹的解释，不是已验证的因果原因。部分不合规回复还提出未经授权的 operation 或 noop/defer，不能只改 ID 就假定所有任务会获服务。

收到输出后程序按事前规则拒绝，保持预算和失败分母；没有中途改提示、填缺字段或重采。对架构的研究判断应先承认协议/提示差异，而不是用总成功率直接声称汇集信息更优或单 Agent 推理更差。后续若引入无歧义任务 ID、明确逐任务示例或更强 schema，需要新登记版本，保留本轮原结果。
