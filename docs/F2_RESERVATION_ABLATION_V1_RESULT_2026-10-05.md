# F2预约机制实验：结果与限定解释

2026-10-05。作者实验与重计已完成，**待独立针对性复审**。本批首次实际运行同一调度器下的预约处理干预，不是又一次只检查旧任务。研究主线仍是多Agent冲突处置、服务与时延。

## 1. 做了什么

同一DeadlineAwareCoordinator、同一公开能力脚本、到达流、信息、权限、容量门、EDF排序函数和命令开销；仅改变晚到water提议返回后是否将尚未实际启动的预约重新纳入排序。已运行服务保持原开始、结束与回执，不发off、不抢占、不重新调用Agent。

固定两个模板×容量紧/足×共同审议延迟0/100ms，8配置、16条正式运行、8对比较。零延迟4对是主实验；共同100ms的4对是敏感性，不作独立家庭样本或池化排名。24条未来信息诊断单列。4条新retain主基线全部精确复现历史Deadline调用、完整事件/状态和结果；旧轨迹仅作复现参照，没有冒充新样本。

## 2. 主结果

下表只列零额外审议延迟主实验。数字均为“replan−retain”，单位秒；均值使用固定4项服务及共同完成K，K=E，覆盖100%。

| 模板与容量 | water完成/响应变化 | 被延后服务 | 全部4项平均自身响应变化 | 全户完工变化 | 按时服务率 |
| --- | ---: | --- | ---: | ---: | --- |
| 01、紧 | −480 | laundry +120 | −90 | 0 | 3/4 → 3/4 |
| 02、紧 | −360 | cleaning +240 | −30 | 0 | 3/4 → 3/4 |
| 01、足 | 0 | 无 | 0 | 0 | 4/4 → 4/4 |
| 02、足 | 0 | 无 | 0 | 0 | 4/4 → 4/4 |

全部16条正式运行均真实完成4项服务；已执行容量违规为0。紧容量下两臂water都迟到，early三项都按时。不能把迟到缩短记作按时成功，也不能把提前完成water叫全户执行加速。

### 模板01、容量紧

water：R=60、D=300秒。retain为S=780.4、F=900.4、自身响应840.4、迟到600.4秒；replan为S=300.4、F=420.4、自身响应360.4、迟到120.4秒。

laundry从S=300.4/F=780.4变为S=420.4/F=900.4，晚120秒但仍按时。dishes和cleaning已实际运行，不变。全户两臂均900.4秒。

### 模板02、容量紧

water：R=120、D=420秒。retain为S=540.4、F=780.4、自身响应660.4、迟到360.4秒；replan为S=180.4、F=420.4、自身响应300.4、迟到0.4秒。

cleaning从S=180.4/F=540.4变为S=420.4/F=780.4，晚240秒但仍按时。meal和laundry已实际运行，不变。全户两臂均780.4秒。

因此既存在固定任务集平均响应改善，也存在个体代价转移；不能说只是等量搬移等待，更不能说所有任务都改善。

## 3. 对A方向支持到哪一步

**当前配置内的机制证据：晚到服务的额外等待不全由实际占用/不可中断作业造成；未启动预约的处理规则本身能改变服务时延分布。**

这次不是拿不同完整政策的差值推测原因：两臂在提交干预快照之前完整输入/事件一致，实际运行区间不变，仅改变未启动预约的处理规则。两个紧容量模板产生明确差异，两个足容量负对照无差异。

但这是“释放未启动预约、重新合并就绪提议并用相同EDF排程”的整体规则干预，不是估计EDF、释放动作、预约身份管理各自的普遍独立贡献。没有证明所有协调方式、真实模型或更多家庭任务都具有同一规律；更没有建立相对既有排程文献的新颖性或顶会竞争力。

### 补充的条件物理界限（事后解释，非预定主指标）

另一个只读程序从干预快照中的已实际运行区间及共同命令下界计算：忽略未启动预约时，模板01/02的water最早可以在300.4/180.4秒开始，最早在420.4秒完成。本次replan达到了这个“固定当前执行前缀”的界限，所以还留下120.4/0.4秒迟到。

这不是在线最优或全局不可避免损失证明。更早的调度决策可能改变这个前缀；不将这一事后解释纳入预登记主成绩，也不因此改变任务参数。

## 4. 100ms共同延迟敏感性

两个紧容量模板的全部实际S/F及成对差值与零延迟主实验相同，因为100ms审议仍在等待实际资源释放的窗口内。两个足容量模板中，两臂water都晚100ms开始/完成，自身响应增加100ms，但臂间差值仍为0；全户完工及按时率不变。

这是两个预定合成延迟水平的局部检查，不是实测重排成本，不支持任意计算/网络延迟下的稳健性。未把零开销当部署能力。

## 5. 完成的核验与公开失败记录

- 8对完整调用及完整干预前缀（含提交快照）一致，已运行服务始终保持。
- 24条不同未来到达/请求/无请求诊断的发布前完整调用与事件前缀一致，不进主服务分母。
- 新审计器重建状态、权限输入、预约代次、物理资源和真实回执；另一同作者程序不导入生成器、引擎或主评分器，直接扫描原始事件核对16条时间/服务及8对差值。**不是独立审阅者验收。**
- 87项相关测试通过：25项新测试/补充探针、62项旧回归；未重跑全套。覆盖同刻审议与启动、审议期间已启动、旧回调晚于新完成、无动作、空K、伪回执和语义前置条件。
- 835项旧材料/代码/结果哈希核验不变。没有API调用、保留集访问、GitHub提交或上传。

两次运行前阻断均保留：初版审计把协议null范围字段与执行语义字段直接比较；修正版保存JSON后又遇到审议下标tuple/list往返不一致。它们是审计器问题，不是调度发现。原入口快照、原锁、失败记录及旧基线gate都保留；当前实际使用implementation_revision=3的锁与baseline_gate_revision3.json。修正只涉及审计语义/序列化及版本绑定，没有改引擎、任务、参数或选择有利运行。正式replan/敏感性都在当前版本4基线门通过之后运行。
