# F2族内结果解读：到达时序、资源竞争与服务时延

2026-10-05。依据已验收F2统计实现及冻结结果，本稿是作者的描述性结果分析，不是新的独立解释审查。只完成F2分析，不在本轮联合F1/F3或修改研究命题。

研究对象是智慧家庭多Agent异步调度中的冲突、服务完成与时延。这里比较的是既有执行／协调政策的调度表现，不设置Agent／LLM与规则的类别优劣命题。

## 1. 材料与对照

2个基础模板，每个配置4项服务：early为3项在0ms发布的服务；water为1项，0ms同时发布或晚到。early是分层名称，不表示永远先执行。water是抽象服务标识，本分析不赋予未经合同定义的家庭设备语义。

| 条件 | 模板01 | 模板02 |
| --- | --- | --- |
| early | laundry、dishes、cleaning | meal、laundry、cleaning |
| water执行时长／资源单位 | 120秒／2单位 | 240秒／1单位 |
| water发布时间：同时／晚到 | 0／60秒 | 0／120秒 |
| water自发布服务时限 | 240秒 | 300秒 |
| water绝对截止：同时／晚到 | 240／300秒 | 300／420秒 |
| 容量：紧／足 | 3／6单位 | 3／6单位 |

总计8配置、32条确定性运行、72对比较、8组四单元；另48条诊断只核对信息边界，不进入性能分母。
固定E=4、early=3、water=1；失败与未启动均保留。时延均从任务自身发布R起算。所有源指针、R/P/S/F和零基事件下标保存在[完整证据](f2_findings_20261005/evidence.json)。

实现验收记录追加为[F2限定验收记录](F2_AGGREGATION_V1_ACCEPTANCE_2026-10-05.json)，引用外部2026-10-05报告及机器审计。原结果的历史pending字段未追溯改写。

## 2. 安全、服务和按时是不同结果

32条运行的实际容量违规持续时间均为0，开始前置条件诊断均有效。仍有8项未完成和10项已完成但迟到：

- 容量紧的4条IndependentMultiAgent运行，每条early仅2/3完成，cleaning和water未启动；总服务2/4完成且按时。
- 其余28条运行全部完成4项服务。
- 10项迟到全部是water，early中已完成服务均按时。
- 容量足的16条运行全部完成且按时，没有门拒绝或容量defer。

因此，本批冲突不是执行超容量，而是容量竞争下的拒绝、预约、排队和个体服务损失。安全门保证不超容量，不能替代服务完成或期限满足。

这些是执行政策完整行为的对照，不将差异归因于Agent数量或语言模型能力。

## 3. 晚到不是统一的“更慢”

下表列容量紧时water自身完成响应F−R，单位秒；箭头为同时发布→晚到。不是绝对完成时刻，也不是总体均值排名。

| 模板／政策 | water自身响应：同时→晚到 | 按时：同时→晚到 |
| --- | --- | --- |
| 01 IndependentMultiAgent | null→null | 未完成→未完成 |
| 01 ConstraintCoordinator | 600.4→540.4 | 否→否 |
| 01 DeadlineAwareCoordinator | 120.4→840.4 | 是→否 |
| 01 GateRetryRule | 600.4→540.4 | 否→否 |
| 02 IndependentMultiAgent | null→null | 未完成→未完成 |
| 02 ConstraintCoordinator | 780.4→660.4 | 否→否 |
| 02 DeadlineAwareCoordinator | 240.4→660.4 | 是→否 |
| 02 GateRetryRule | 420.5→300.5 | 否→否 |

### 3.1 期限感知排程：发布顺序改变紧服务的机会

DeadlineAwareCoordinator在容量紧、同时发布时，两个模板均early 3/3按时、water 1/1按时。晚到后，early仍3/3按时，但water均迟到：

- 模板01：water等待从0.4秒增至720.4秒，自身完成响应增加720秒；绝对完成时刻从120.4秒变为900.4秒。
- 模板02：water等待从0.4秒增至420.4秒，自身完成响应增加420秒；绝对完成时刻从240.4秒变为780.4秒。

当前实现等待已发布任务的提议返回后，对当前待处理批次按截止排序并安排容量预约。它不读取未来请求，也不会因晚到请求而重排已建立的整个预约计划。实现线索：event_simulator_v7.py的dispatch_proposal（容量预约）与try_dispatch_deadline_batch:596（已发布批次）；本轮仅阅读，未运行或修改模拟器。

这里“同时／晚到”同时改变了信息可见时刻、water绝对截止以及由先前决策形成的排程背景，虽然自身服务时限保持一致。因此只能报告预定到达时序对照，不能把全部差异归因于单一的信息价值或不可中断性，也不能称所有期限感知算法均有此性质。

### 3.2 响应缩短，不等于执行加速

ConstraintCoordinator和GateRetryRule的4对容量紧发布对照，所有任务的绝对开始、完成和执行时长完全不变。

例如模板01的water都是480.4秒开始、600.4秒完成。晚到使R从0改为60秒，响应从600.4变为540.4秒；模板02对应缩短120秒。**这是自发布时钟的真实差异，不是排程把任务执行得更早。**

water绝对截止也随发布时刻后移相同幅度，但这些运行仍迟到。不能把更小的迟到或响应数值概括成调度能力提高。

模板02 GateRetryRule晚到water只迟到0.5秒：R=120、S=180.5、F=420.5，截止420秒。它符合冻结硬截止计分，但这一边界现象应连同合成命令时序与裕量报告；目前没有运行新的开销或期限敏感性实验。

## 4. 正在执行与尚未执行的预约都需看，但不能混为一谈

晚到时实际占用仅统计S<L<F。未来预约不是L时刻的物理负载。

模板01、容量紧、DeadlineAwareCoordinator：

- L=60秒时，dishes和cleaning正在执行，合计2单位；water需2单位，容量3，无法在该背景下立即开始。
- laundry尚未启动，却已于0.3秒预约在300.4秒开始，持续480秒，占2单位。
- water于60.3秒获得返回，随后被安排到780.4秒开始、900.4秒完成。
- laundry预约在L时刻不能算“已执行不可中断服务”；但它是当前预约政策随后安排water时所保留的排程背景。

模板02、容量紧：

- L=120秒时，meal 2单位与laundry 1单位正在执行，占满容量3。
- ConstraintCoordinator及DeadlineAwareCoordinator已预约cleaning在180.4秒开始，占2单位，持续至540.4秒；water被安排在540.4秒开始。
- GateRetryRule没有相同的未来预约，water在180.5秒开始，cleaning到420.5秒才开始。water早359.9秒完成，但cleaning晚240.1秒完成，两者early均按时；全户完工780.5秒与780.4秒几乎相同。

这支持“看当前物理状态还不够，还要核对排程承诺及后续处置”的分析角度。但本轮没有同政策下的预约重排消融，不能量化预约机制独立贡献，也不把已存在预约解释成合法动作不可更改的普遍约束。

## 5. early更早／全户更早，可以伴随water更慢

同一DeadlineAwareCoordinator的模板02容量紧发布对照：

- 同时发布：laundry 240.4秒开始，840.4秒完成；water 240.4秒完成且按时；全户840.4秒完成。
- 晚到：laundry 0.4秒开始，600.4秒完成，早240秒；water自身响应增加420秒并迟到360.4秒；全户780.4秒完成，反而早60秒。

所以，**更早全户完工并不保证晚到服务更好；early完成改善也可能掩盖water服务下降。** 这是预定发布对照的描述，不是同一已知请求集合下的纯排序消融。

模板01则有另一种形态：晚到cleaning比同时发布早120秒完成，water自身响应增加720秒，全户反而晚120秒完成。不能只选择模板02的“总完工更早”例子；两模板都保留。

## 6. 容量足是必要的负对照

容量足的16条运行，所有early和water均完成且按时。8对同时／晚到比较：

- water等待均为0.4秒。
- water自身响应保持不变：模板01为120.4秒，模板02为240.4秒。
- water绝对完成时刻只随发布时间后移60／120秒。
- 全户完工保持不变：模板01为480.4秒，模板02为600.4秒。

四种政策在这些配置中具有相同的逐任务启动／完成时刻，尽管内部提议处理顺序可能不同。**晚到本身不足以制造性能损失；结果依赖资源背景与具体排程政策。**

## 7. 四单元与完成集合：解释时必须同时展示资格

8组四单元顺序固定为容量紧同时、容量紧晚到、容量足同时、容量足晚到。交互定义为“容量在晚到下的效果”减“容量在同时下的效果”。

- DeadlineAwareCoordinator两个模板的按时服务率依次为1、0.75、1、1，交互均+0.25：扩大容量在晚到条件下修复了这批按时服务差异，而同时条件下本来全部按时。
- water自身响应的交互分别−720秒、−420秒。这些是预定网格内的描述，不是普遍因果系数。
- ConstraintCoordinator／GateRetryRule按时率依次0.75、0.75、1、1，按时交互为0；water响应交互仍非0（模板01 +60秒、模板02 +120秒），反映自发布时钟与容量条件的组合。
- IndependentMultiAgent按时率为0.5、0.5、1、1。两个四单元的K只有2个early任务，覆盖率50%；water未在紧容量臂完成，其共同K时延及交互为null，不能以完成子集很快掩盖未完成。
- 其余6组K=E，覆盖100%；没有借不同完成子集计算四臂时间差。

不创建跨政策时延总排名或跨族总分。

## 8. F2得到的简洁收获

1. **到达时序的影响取决于资源与排程背景，不是“晚到必然更慢”。**
2. **晚到服务的结果需要同时看已启动服务和未启动预约。**
3. **early、water与全户完工必须分开，不能用整体更快代替个体按时。**
4. **自发布响应变短，可能没有任何绝对执行加速。**

这些是本批F2的条件性发现，不替用户重新定义项目主命题。未开展F1/F3联合分析，也未设计新的模型／规则类别比较。
