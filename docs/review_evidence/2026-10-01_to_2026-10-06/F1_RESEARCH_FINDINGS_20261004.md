# F1族内研究发现：协调改变了什么

2026-10-04。依据已通过实现审查的72条确定性运行、168对比较及18组四单元。本稿是合成开发网格的描述性解读，不作策略总排名。计算前重新核对受审文件哈希。

可复算明细：[配置/策略及证据数据](./F1_FINDINGS_DATA_20261004.json)、[逐任务匹配差值CSV](./F1_FINDINGS_TASK_DELTAS_20261004.csv)、[实现审查](./F1_AGGREGATION_V1_REVIEW_20261004.md)。原始结果基目录：`https://github.com/xxc0304/homecoord-bench/blob/main/docs/f1_aggregation_v1_20261004/`。事件下标均从0开始。

## 服务结果与容量分层

所有72条运行均完成全部预定任务，实际容量违规持续时间和超额资源积分均为0。因而这批材料没有识别出服务完成率或物理过程安全的策略差异；共同安全门、完整重试与当前参数都限制了解释范围。零违规不能作为更复杂协调改善安全的证据。

### 发现1：协调将准入介入从拒绝/重试转为事前排队

三任务紧容量配置中，GateRetryRule每次运行有1次门拒绝、1次重试入队；两协调策略各有1次defer、无动作拒绝。五任务紧容量中，GateRetryRule按order0/1/2有3/2/2次拒绝与重试；ConstraintCoordinator对应3/2/2次defer；DeadlineAwareCoordinator均为3次defer。容量足时这些拒绝/defer/重试均为0。

24个紧容量策略配对都呈现“拒绝减少、defer增加”，24个足容量策略配对这些数量不变。这是介入路径变化，不是冲突完全消失：共享资源仍要求串行等待，拒绝也未造成最终服务丢失。

三任务tight/base/order0的dishes是小而明确的例子：GateRetryRule于181200ms开始、481200ms完成；ConstraintCoordinator于181100ms开始、481100ms完成。对应源结果的task事件为Gate start e22/complete e24，Constraint start e18/complete e20。两者均按时；100ms差来自已提交的排队/命令执行路径，不可叫真实推理或API低时延收益。

### 发现2：容量放宽主要减少等待，部分场景也改变按时结果

36个容量配对（紧→足）全部全户完工更早，差值范围为−479400至−200ms；主完成率不变。32对按时率不变，4对提高20个百分点，均对应五任务基准期限下GateRetryRule或ConstraintCoordinator的order1/2。

服务动作的配对执行时长均不变。改善体现在真实启动安排和排队，不是设备周期更短。容量干预也不是协调策略改进；36对包含期限和策略分层，不能当36个独立家庭样本。

## 期限与返回顺序

### 发现3：宽松期限的按时改善来自评分边界变化

36个基准→宽松期限配对的拒绝/defer、逐任务启动等待、完成时延及全户完工均不变。32对按时率不变，4对提高20个百分点。增加1200000ms截止预算让原本已完成但迟到的water变为按时，没有让执行更快。

18组四单元中，所有任务四臂均完成，因此本批实际K=E；共同K仍必须保留为合同规则。容量×期限的时延交互均为0；非零按时率交互出现在五任务GateRetryRule/ConstraintCoordinator的order1/2，为−0.2：基准期限时容量足改善按时率，宽松期限下该差异归零。这表示截止边界与容量约束的联合影响，不是额外的计算能力收益。

### 发现4：返回顺序影响迟到对象，也暴露全户完工与个体代价的分离

五任务紧容量基准配置的water截止为360000ms：

| 策略 | order0完成/迟到ms | order1完成/迟到ms | order2完成/迟到ms |
|---|---:|---:|---:|
| GateRetryRule | 240900 / 0 | 661300 / 301300 | 661100 / 301100 |
| ConstraintCoordinator | 240900 / 0 | 720900 / 360900 | 901300 / 541300 |
| DeadlineAwareCoordinator | 241700 / 0 | 241700 / 0 | 241700 / 0 |

这不是完成集合选择效应：water都真实完成。ConstraintCoordinator在order1让全户比GateRetryRule早299800ms完工（901100对1200900ms），但water晚59600ms完成；order2全户早239800ms，water却晚240200ms。全户更快不能代替逐任务服务体验更好。

可定位例：order1 water的Gate start e37/complete e41，Constraint start e32/complete e33；时间值、源槽位及每任务全部事件已保存。不能把更多迟到自动解释为永久拒绝或服务失败。

DeadlineAwareCoordinator在本批每配置3个顺序下的启动/完成安排保持一致；GateRetryRule与ConstraintCoordinator在部分紧容量配置显著受顺序影响。这里只观察了3种固定顺序，不证明任意异步返回下的鲁棒性。它们也不是随机种子或真实模型延迟分布。

## 期限优先的收益与代价

五任务紧容量基准中，DeadlineAwareCoordinator在order1/2将按时服务率从4/5变为5/5；全部48个策略配对中，仅这2对按时率提高，其余46对相同。没有策略配对改善最终完成率。

代价并不统一。三任务紧容量order0中，它让dishes比GateRetryRule早179900ms完成，却让laundry晚180400ms完成，全户也晚180100ms完工；两臂都全部按时。五任务紧容量order0中，全户晚240700ms（1141700对901000ms），laundry完成从721100变为1141700ms，按时率仍同为5/5。相反，五任务order1它的全户完工也比GateRetryRule早59200ms。期限优先不是始终更快或始终更慢。

可支持的表述是：在这批紧容量、特定返回顺序的确定性世界里，期限优先安排保护了更急任务的截止，重新分配了等待；是否改善某个个体和全户完工取决于情境。无法据此宣布策略总体优越、LLM必要或多Agent本身产生增益。

## 可以用于研究主张的范围

可报告：“共同安全门下，协调方式可将门拒绝/重试转为排队，并在同样完整完成服务时重分配逐任务等待与截止风险；介入减少、全户完工和个体按时是不同结果。容量与期限对照能分别揭示排队效应和评价边界变化。”

不可报告：统计显著或普遍优势、真实家庭安全/节能、真实计算时延、独立随机泛化、不可避免损失、统一策略排名。全部结果依赖2模板、固定服务周期、共同门、3脚本顺序及合成截止。本文没有新增模型或模拟器运行。

下一步F2应继续这一问题，改为“已启动的非抢占服务遇到晚到请求时，等待与截止风险怎样变化”，先固定统计合同，再提交事件适配器。不能把离线知晓未来的排程当在线基线，也不能让反事实回放加入主率分母。
