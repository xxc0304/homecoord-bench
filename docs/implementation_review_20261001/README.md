## 每个trace文件包含什么

| 字段 | 内容与审查用途 |
|---|---|
| episode | 原冻结输入，含初态、权限、工具、grounding、约束、发布与截止。不是修订版本。 |
| calls | 实际传入脚本的request、返回decision与声明逻辑延迟；核对request_id、task_id、主体、状态版本、允许工具和可见输入。 |
| trace.events | 完整有序事件。含发布、请求、提案返回、等待、拒绝、启动、状态更新和完成；proposal_id关联一次动作尝试。 |
| trace.final_state/version | 最终状态及版本，供逐事件重放核对，不替代过程检查。 |
| reported_result | 原执行器/评估器报告，完整保留，包括旧字段。不能默认全部字段口径相同。 |
| independent_event_recount | 单独重计的实际启动/完成、等待、时延、迟到、暴露、实际执行区间和完成回执；不用生产task_response_metrics计算。 |
| dependency_metrics | 仅依赖组的生产回执/等待/阻断指标；与事件重计及旧记录核对。 |
| historical_comparison | 对旧保存字段的一致性核对，不是新样本。 |
| reviewer_acceptance | null，留待审查者。 |

事件和调用日志关联请求及提案ID，但依赖仍是单次任务级工作流，没有实体衣物batch_id。实际执行区间采用[start,end)，不是把已排好的未来预约当作已运行占用，也没有实测功率或能耗。C3-F1旧power_kw为抽象预约单位。

## 本轮要求核查什么

### F1：8配置全部检查

- 每个脚本只能提自己授权的服务动作；F1调用不包含action_template、required_action或acceptable_actions评估提示。
- 已公开成本与实际持续时间/占用一致；开始不早于发布。工具idle前提应在开始效果应用前检查，不要因同刻设备被置running而误判启动前提。
- 依据实际启动至真实完成的半开区间重算容量；必要排队后按时仍成功。
- 服务要有匹配动作的真实完成回执；合法off不算服务。终态complete不能代替动作身份和回执核对。
- 自身发布至启动为等待，自身发布至完成为时延，完成-截止的正部为迟到；缺失启动/完成保持null。全计划完成不能遮盖个体超期。

### 依赖：5配置限定单次范围

- 提前请求及合法提案可以等待，但dry启动前必须已有有效wash完成回执并满足washed状态。
- LATE_REQUEST的dry只在5000ms发布；不得提前执行。EARLY与LATE绝对截止相同，不称等剩余预算的时延对照。
- FORGED_STATE的450ms外源washed=true不得替代真实回执；按事件顺序检查，不只看最终washed状态。
- 容量紧/足的dishes是独立服务；洗→烘必要串行不是容量冲突，后继与独立分支才形成竞争。
- 无重试策略可能合法拒绝但未提供全部服务，保留false/null；不能因为安全门成功就算服务完成，也不能用规则足够的结果证明LLM必需。
