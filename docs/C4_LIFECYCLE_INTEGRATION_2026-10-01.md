# C4 停止、撤回与恢复：统一事件执行器 v2

日期：2026-10-01。状态：作者定义的离线开发验证；非真实设备、非模型性能、未独立双审。无新增 API、未打开保留测试、未上传 GitHub。

## 实际交付

第一阶段的清洁/灌溉任务，现在已在**版本化的统一事件运行时**接入停止请求、停止确认、预约释放、旧完成事件作废、清洁从零重启、灌溉请求撤回。它们与提案返回、权限检查、工具 grounding、共享安全门、容量调度及逐任务完成指标处在同一个事件队列，不是另一个独立解析恢复探针。

为保留已完成架构试验的哈希锁，旧 `runtime/event_simulator.py` 未改动；新入口为 `homecoord_bench.task_revision.event_simulator_v2.run_event_simulation`。v2 是从冻结 v1 源码派生的版本化执行器，**尚未替换旧 CLI 默认入口**。调用旧入口仍是旧行为。无生命周期配置时，两版本在14个原语义情境及24个 C3 开发情境、各4策略上的152组轨迹/评分一致性检查通过。后续推广应明确迁移并锁新版本，不暗中修改旧试验。

## 生命周期合同与真实事件

- 明确配置 `simulation.lifecycle_contracts`：任务ID、可观察有效条件、`restart_from_zero` 或 `withdraw`、停止确认延迟、重启等待、停止效果。要求严格工具合同和唯一动作 grounding；停止只能把授权设备置于已声明的静止状态，不能写服务回执。
- 本地执行器看到已发布请求的有效条件失败，生成 `stop_requested`。动作在确认前继续运行、占用容量并产生真实的过程暴露，不在请求时提前视为停止。
- 确认后才生成 `action_stopped` / `reservation_released` / `completion_invalidated`。原队列中稍后到达的完成事件成为 `completion_discarded`，不应用其效果、不写完成回执。
- 清洁等待当前占用条件解除，再重用同一任务所有者的已授权提案；新 proposal ID 和当前状态版本，重新验证权限/工具/状态，并支付命令延迟，从零执行完整周期。没有额外模型调用，也不假装是模型重新规划。
- 灌溉在降雨后永久撤回该请求；雨停不会自动复活。请求未启动时不需要停止确认；请求已经完成后，不追溯撤回。
- 停止属于共同的可信本地联锁底座，不能归功于某个 Agent/协调策略。本轮第二 Agent 仍只是独立服务，不证明多 Agent 因果协作必要性。

## 匹配离线结果

两场景×五情境×四策略×功能关闭/开启，共80次脚本执行、40个匹配对。策略为 Independent、Constraint、DeadlineAware、GateRetry，均有相同的共享安全门。使用答案模板和固定300ms提案延迟；不属于80个独立模型样本，也没有新任务结构。

| 指标 | 生命周期关闭 | 生命周期开启 | 解释 |
|---|---:|---:|---|
| 主请求正确处置 | 28/40 | 40/40 | 按有效请求完成或明确撤回计，不等于所有动作完成 |
| 完成的动作服务 | 72/80 | 72/80 | 清洁恢复增加完成，正确取消灌溉减少完成；总率本身看不出改进 |
| 零正时长违规情境 | 32/40 | 32/40 | 仍有8个执行中情境产生暴露，不能声称全部安全 |
| 每个执行中情境违规暴露 | 2400ms | 200ms | 本轮假设停止确认200ms，不是实测联锁性能 |

开启后的8条执行中轨迹均停止确认并作废旧完成事件。清洁4条执行中重启、4条启动前拒绝后重试均完成；灌溉4条执行中停止和4条启动前撤回均正确处置。每条保存轨迹均通过独立状态重放、完成/取消重计、预约释放和违规积分审计。

代表性时间线：工作开始400ms → 失效事件1000ms → 停止确认1200ms → 原完成3400ms被丢弃。清洁在住户5000ms离开后，5100ms重新开始、8100ms完成。灌溉没有重启或完成回执，完成时延保持 null。

所有时长/功率是作者定义的抽象服务合同。暴露下降只说明代码遵循该合同，不证明实机200ms可停，也不证明 LLM 优越性。

## 边界与评分修正

30项新增单元测试，全套332项通过。其中一项覆盖120组事件时刻/停止延迟组合：两场景×10事件时刻×6延迟（0/1/100/200/2400/3000ms）。另覆盖重复无效事件、两轮取消、条件在确认前恢复、条件在排队重启后再次失效、永不恢复、雨停不复活、无关更新、权限/负延迟/回执越权，以及篡改轨迹的负测试。

边界约定：动作有效运行区间为 `[开始, 自然完成)`。同刻无效事件先于动作开始时，会阻止启动；恰好自然完成时不发起停止。自然完成与停止确认同刻时，**自然完成先于确认**，记录 `stop_ack_too_late`，不倒写取消。零停止延迟只保证零正时长暴露，不承诺没有瞬时不安全中间状态。

取消后不得沿用旧预计完成时刻计服务或期限：新指标来自真实 `action_completed`。例：清洁重启8100ms完成、截止6000ms，应超期2100ms；不能把被取消的旧尝试1200ms结束当作按时完成。合理撤回另计处置，不充当动作服务或按时完成；不必要的旧基线灌溉即使完成，也不算正确处置。

预约释放测试加入第三项容量效果：停止确认1200ms释放容量，GateRetry 等待任务支付100ms命令延迟、1300ms启动，而不是等原3400ms完成。**现有已排好的未来预约并不自动重新压紧**；不同调度策略仍可继续等待原排期，不能承诺所有策略都获得同样的提前启动收益。

## 尚未完成与下一步

当前支持单一明确动作、eq有效条件与上述四种策略；暂不支持多合格模式、计时计算工作队列/预先批计划与生命周期的组合。重启复用提案，不支持保留进度的暂停续作、动态权限变化、复杂补偿、模型在线修复或自动重排所有未来预约。机器人/水泵真实停止确认与安全状态仍需要来源或实机验证；人类独立双审尚缺。

接下来先补洗→烘的任务依赖：区分请求发布、前提满足与真实可执行时间，验证未洗完不能烘、洗涤取消不能释放依赖、强规则按时服务。之后评估 C2 环境接口，保留未校准的合成探索身份；再组织独立任务审查和同信息强规则对照，任务稳定后才登记新的模型小验证预算。
