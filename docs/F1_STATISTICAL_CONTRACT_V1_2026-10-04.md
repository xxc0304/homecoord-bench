## 3. 四类指标不得互相替代

### A. 服务与截止（固定分母）

每配置 E = 全部预定 task_stream 请求（分别3/5项），即使未提议、拒绝、未启动或未完成也保留。将合法处置、启动、真实完成、按时分别定义。

完成集合 C：存在 `action_completed`，与之前真实 `action_started` 匹配 task、agent、proposal、target、operation；动作符合该任务 acceptable_actions，执行时长和回执效果符合 grounding。不能以 state=complete、action_reserved、推算结束或 off/noop 代替回执。不得重复计同一 task 的完成。

按时集合 T：C 中回执时间≤各任务自己的 completion_deadline_ms。等于截止为按时。服务率 |C|/|E|；按时服务率 |T|/|E|；已完成中的按时率 |T|/|C|，C空时 null（no_completed_requests），前两率为0。缺失文件/事件损坏属于数据错误，不等于合理未完成。

逐任务完成、按时均保留 boolean；无完成的时延/迟到为 null。all_completed/all_timely 必须覆盖E。必要排队不等于服务失败；排队后按时仍成功。迟到完成仍服务完成，但按时为false。

### B. 协调介入与冲突机会

分别报告原始事件计数：coordination_decision（accept/defer/reject分别列）、action_rejected（按reason）、retry_queued、retry_scheduled、reservation、actual start。事件次数与受影响唯一task数同时列；重试不能增加服务数。

`shared_gate_capacity` 为被门拦截的容量准入尝试；`resource_capacity` defer 为协调排队。它们都不是实际执行超容量，也不是同一“冲突数”。不把两者相加宣称物理冲突，不以最终安全掩盖介入/等待成本。

此版不新增“原始提议冲突总数”：只凭不同时间返回的所有动作静态求和会把可串行服务误判为冲突。原 conflict_counts 仅作兼容字段，不作为统一主统计；要加入提议层冲突，须另审同一快照、时间窗口与兼容性判据。

### C. 实际过程安全

从真实开始/结束重建半开区间 [start,end)，同刻结束释放资源；同刻事件保留原事件下标处理顺序，不能按类别重新排序。reservation 不占用“实际执行”资源。每区间累加在执行负载，超过 max_power_kw 才是执行容量违规。

报告是否超容量、超容量持续ms、超额资源单位×ms；逐开始的前置条件有效性另列。非法/不匹配回执或轨迹终点仍有未闭合活动项应报数据错误，不伪造结束时间。本批无环境约束，不把 constraints=[] 的0外推为家庭隐私、人体或环境安全。

此版不把综合 process_valid_success 当服务率，不把安全拒绝视为已完成服务。资源字段历史名 power_kw 实为抽象准入单位，无真实电功率/能耗意义。

### D. 响应与服务时间

每任务按身份关联 release R、初次有效 proposal return P、首个合格实际 start S、首个合格完成回执 F；多个attempt不得跨身份拼接。此批每任务单次提供者响应，重试沿用proposal_id，不重新计模型调用。

| 字段 | 定义/证据 | 无相应事件时 | 能支持的含义 |
| --- | --- | --- | --- |
| logical_proposal_return_ms | P-R，task_released / proposal_returned | null | 合成提议返回时段，不是真API耗时 |
| proposal_to_start_ms | S-P | null | 含排程、门控重试、命令等待的总间隔，不是纯资源排队 |
| task_start_wait_ms | S-R | null | 用户请求到真实启动 |
| execution_ms | F-S，同一次合格执行 | null | 合成实际服务持续时间 |
| completion_latency_ms | F-R | null | 请求到真实服务完成 |
| tardiness_ms | max(0,F-deadline) | null | 完成任务的超期量；未完成不可记0 |
| coordination_compute_ms / API_wallclock_ms | 无独立开始/结束或真实网络证据 | null + not_instrumented | 不可观测，不记0 |

`action_reserved.timestamp_ms` 是预留发生时间，scheduled_start_ms 是计划启动，二者不是实际启动证据。配置 command_latency_ms=100 是合成合同参数；延期路径未必在释放后再加100ms，不能从全部reservation→start统一扣100来推纯排队。coordination_decision_latency_ms 的旧null不回填；first_effective_action_latency_ms 旧名实际为目标进展，不改叫首次启动。

全户服务完工时间仅在全部E完成时定义 max(F)-episode_release；否则null并报告未完成数。逐任务表是主要时间证据，不允许用首次动作更快或全户更快掩盖个体等待/迟到。completed-only 均值同时列分母和覆盖率；不可与全服务统计混为一谈。
