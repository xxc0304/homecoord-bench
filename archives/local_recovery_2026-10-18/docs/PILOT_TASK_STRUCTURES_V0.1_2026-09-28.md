# HomeCoord-Bench 12 种试点任务结构 v0.1

日期：2026-09-28。状态：**待实现、待审核的任务设计**，不是已经生成的 36 条正式数据，也不是论文实验结果。本稿用于决定先做哪些独立结构，不能按某一基线是否失败筛选任务。

## 设计原则

研究问题是“异步多 Agent 协调何时有净价值”。C1 同设备、C2 共享环境效果、C3 资源容量是机制；C4 状态失效是动作生命周期维度，可叠加在前三类上。Agent 数目只是任务结构的一个属性。只有局部目标、工具或信息边界确实不同的角色才计为不同 Agent。每种结构至少包含正常、临界、压力条件，并尽量一次只改一个条件；混合机制采用小型消融而非声称只改一个变量。不同参数版本属于同一个结构，不算独立家庭样本。

下表的“来源要求”是升级到正式数据的准入条件，未满足时仅能标为合成机制题。已做过的 C1／C2／C3／C4 小试验只是设计起点，不自动成为正式 benchmark。

## B. 多任务协调：6 种三到五 Agent 结构

| ID | Agent／任务与机制 | 配对条件与真正新增的结构 | 来源／当前状态 |
|---|---|---|---|
| M01 | 做饭、烘衣、洗碗三个专业 Agent 竞争受管电力。C3。 | 低／临界／高容量；三者中某两项可并行，另一项须等待。改变提案到达顺序而保持任务不变，测部分并行、排序与期限。 | 已有三 Agent 固定负载探索试验；正式任务需设备阶段功率、容量口径和住户期限依据。 |
| M02 | 洗衣 Agent 完成洗涤后触发烘干 Agent，热水 Agent 同时占用容量。依赖＋C3。 | 相同三个任务下变动共享容量，并对比烘干提案在洗涤完成前／后返回；评测是否错误预留、无谓空闲或错过期限。 | 洗烘前后依赖可核实；阶段功率、任务期限与提前预约语义需来源。不能让执行器泄漏未来完成时间。 |
| M03 | 舒适 Agent 控 HVAC，能源 Agent 请求关闭 HVAC，EV Agent 占用同一预算。C1＋C3。 | 用 2×2 最小消融：能源请求重叠／不重叠，容量紧／松；比较单机制与耦合机制。不能将四臂当四个独立样本。 | C1 命令时序和 C3 负载均需分别审核；能源目标必须可判定。 |
| M04 | 通风 Agent 开窗、气候 Agent 制热、热水 Agent 使用电力。C2＋C3。 | 分别改变通风需求和功率余量；看过度串行是否损失温度期限，以及环境影响与容量约束是否相互改变最佳排序。 | 需要联合物理轨迹和功率资料；在补齐前不进入现实物理主结果。 |
| M05 | 两个房间的舒适 Agent 分别调节各自 HVAC，热水 Agent 也占用共享容量。C3、多区域服务。 | 不同房间请求同时／错峰到达，容量相同；记录各任务等待与最差房间服务，不只报总成功率。 | 需各房间设备额定功率、相应效果模型及房间需求；避免只用相同任务复制两个 Agent。 |
| M06 | EV 充电、热水、烘干三个 Agent 共用容量，但至少一个任务有多档功率或允许安全暂停。C3、可调整动作模式。 | 保持任务与总容量不变，对比只有固定档位／允许低档位／允许暂停恢复三种设备能力；检验排队与降档并行的服务—时延取舍。 | 这是能力变化实验，不能与 M01 的固定负载样本混算；每种档位、暂停回执与恢复损耗都须有设备契约或明确标为合成。 |

## C. 动态执行：3 种状态变化结构

| ID | Agent／任务与机制 | 配对条件与要测的决定 | 来源／当前状态 |
|---|---|---|---|
| D01 | 清洁 Agent 运行机器人；占用观察 Agent 异步报告住户将进入或已进入。C4。 | 同一住户进入事件下，改变通知提前量：足够提前／决策边界／事后才报告；另有无事件对照。测是否避免启动、能否安全停机及离开后恢复服务。 | 已有事件后模型消息试点，表明事后 LLM 报告过慢；须定义机器人停止回执与占用来源。紧急安全互锁使用直接传感器规则，不靠 LLM。 |
| D02 | EV、热水、烘干三个任务 Agent 正在预约或执行；能源监测 Agent 异步报告可用容量变化。C3＋C4。 | 容量变更发生在提交前／运行中／完成后，保持负载任务一致；测预约失效、调整、未服务任务恢复。 | 必须有容量变更的合理原因、监测 Agent 的观测和消息时延；设备是否能暂停或降功率需明确。 |
| D03 | 舒适 Agent 请求 HVAC、能源 Agent 管理峰值窗口、占用 Agent 报告住户返家。C1＋C4。 | 返家报告在关机提案前／后、命令生效前／后到达；评测权限、状态版本、取消与服务。 | 要定义“返家后舒适服务”的时间窗口和反馈。占用消息必须真正进入另一 Agent 决策；否则只是外生状态题。 |

## 正式任务的统一字段与审核

每条任务保存基础结构 ID、独立家庭／设备配置 ID、参数来源等级、任务文本、Agent 各自观察和权限、工具候选、初态、任务释放、提案返回、外生事件、动作开始／完成效果、约束、必要服务、截止时间、可中断／恢复语义、配对组 ID，以及模型不可见的验证器答案。允许多个安全有效轨迹，不把唯一预设动作当唯一正确答案。

准入顺序：①检查目标和单动作合法性；②用信息不泄漏的全知离线可行性检查确认至少存在安全可行计划，或明确标为不可行任务；③两名审核者在不看策略结果时独立判断自然性和来源；④固定版本与配对条件；⑤再运行基线和模型。不得因为强规则成功而删题，也不得因为它失败而偏收题。

## 评测设计与规模

试点规模是 12 个结构 × 每结构约 3 个配对条件，约 36 个 episode；M03 的 2×2 消融使实际数目略多。这个数量只够验协议和发现设计错误，不够推断真实家庭冲突频率或声称顶会证据充分。正式规模由结构多样性、参数来源和统计精度决定，不靠大量随机种子替代独立配置。

同时做两种隔离比较：同一任务集分配给 1／2／多个 Agent，测组织架构影响；固定 Agent 组织后增加任务数和冲突图复杂度，测工作量影响。中央与专业 Agent 的可见信息差异必须报告。所有策略共用安全门控；强基线包含设备锁、状态／容量约束、期限排序与容量感知规则。固定同一提案及延迟的回放用于归因协调决策；完整模型运行检验自然语言提案和真实 API 调用耗时，两者不混算。

主结果按安全、必要任务服务、按时、首次有效动作延迟及尾部、全部完成时间、调用成本分别报告。用配对差值和按结构聚合的区间，不把同一模板的多次回放当作独立样本。若强规则在真实审核任务上仍饱和，记录其适用边界，不为了提出新算法追加人为冲突。
